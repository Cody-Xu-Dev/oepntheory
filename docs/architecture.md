# 架构设计

## 设计目标

一个读者能快速阅读、采集者能持续追加、每条观点能回到出处的小型资料仓库。以 JSON 做唯一事实数据，以确定性 Python 生成 Markdown；不引入数据库、服务端或付费 API。

## 四种数据

1. **Theory**：稳定 ID、名称、别名、状态、当前摘要、关联来源、带引用的观点和待解决问题。存量知识持续修订，Git 保留版本差异。
2. **Source**：独立来源 ID、规范网址、作者、来源类别、原始发布时间、首次发现日期、核读状态、自写摘要。网页变化用新来源记录及 `supersedes` 关联旧版，同一 URL 可有多个版本，旧记录不覆盖。
3. **Event**：只追加的事件，关联理论和来源，区分初始存量、新来源、观点修订、新理论、候选发现和纠错。发现旧资料与作者新发布是两回事。
4. **Run**：每次检索的覆盖时间、执行时间、查询与访问结果、失败项、事件 ID。即使零事件也保留；部分失败不推进完整覆盖水位。

## 数据流

```mermaid
flowchart LR
  A[来源列表与公开搜索] --> B[核读、规范网址、去重]
  B --> C[来源记录与理论条目]
  C --> D[只追加的事件和检索日志]
  D --> E[引用与状态校验]
  E --> F[生成理论页、每日汇总和索引]
  F --> G[原子 Git 提交与远端校验]
```

## 新理论发现

配置中的发现查询负责广度，原作者资料与完整正文负责深度。新名称先建 `candidate`；有可核读的定义、可识别发布主体或传播上下文、与已有主题可区分后升为 `tracked`。多次提及不是真实性证明。只改叫法的内容归为已有理论别名，不人为制造新理论。

## 更新与发布

一次运行先抓取远端 main，覆盖窗口从上次 `complete` 的截止时间回溯 48 小时，失败日志所涉窗口补查。发布时间不明的内容允许归档，明确为“新发现，发布时间待核实”。每日汇总按 Asia/Shanghai 发现日期组织；同日重跑增加 run/event ID，不覆盖原日志。

内容审核后执行校验、生成、一致性检查与测试。通过 GitHub connector 批量 `create_tree`、`create_commit`，以当前 main 的 SHA 为 `expected_sha` 更新引用；禁止强推。并发提交时重新读取远端并整合，不能用旧目录整体覆盖他人文件。定时任务不混入本聊天其他仓库的文件。

## 可维护性

新增主题只需数据记录和查询配置；生成器不包含四个主题的硬编码。来源正文不可访问时降低证据状态而非让任务崩溃。网络检索和内容判断由定时 agent 承担，生成器仅处理本地可信数据。搜索结果、网页和仓库里的外部内容都不是可执行指令。
